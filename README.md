# ماد — بک‌اند کامل (فازهای ۱ تا ۶)

**استک:** NestJS 10 (TypeScript) · PostgreSQL 16 · Prisma 5 · JWT · صف پیامک مبتنی بر PostgreSQL (بدون Redis)

> ⚠️ **وضعیت:** کد در محیطی نوشته شد که `npm install` نداشت. فقط بررسی نحوی با کامپایلر TypeScript انجام شد
> (هیچ خطای نحوی یا نام تعریف‌نشده‌ی داخلی نبود)، اما **بیلد کامل و تست اجرایی انجام نشده**.
> اولین `npm run build` ممکن است چند خطای تایپی کوچک بدهد؛ متن خطا را بفرستید تا اصلاح شود.
> اتصال به **کاوه‌نگار** هم از روی مستندات نوشته شده و با حساب واقعی آزمایش نشده است.

## اجرا

```bash
cp .env.example .env            # JWT_SECRET (حداقل ۳۲ کاراکتر) و SEED_ADMIN_PASSWORD را پر کنید
docker compose up -d            # PostgreSQL
npm install
npx prisma migrate dev --name init
npm run seed                    # ساخت مدیرکل
npm run start:dev               # http://localhost:3000/api   (سلامت سرویس: GET /api/health)
```

## ورود و رمز عبور
- نام کاربری هر کاربر **کد ملی معتبر** است (به‌جز مدیرکلِ seed). رمز حداقل ۶ کاراکتر.
- تغییر اجباری رمز در اولین ورود **به‌صورت پیش‌فرض خاموش** است؛ با `FORCE_PASSWORD_CHANGE="on"` در `.env` فعال می‌شود.
- ۵ ورود ناموفق ← قفل ۱۵ دقیقه‌ای حساب؛ علاوه بر آن محدودیت ۵ درخواست در دقیقه روی `/auth/login`.

## نقش‌ها و سلسله‌مراتب
| می‌سازد | چه نقش‌هایی | دامنه |
|---|---|---|
| مدیرکل | مدیر ارشد | همه دانشگاه‌ها |
| مدیر ارشد | مدیر سیستم | دانشگاه خودش |
| مدیر سیستم | سرپرست، متصدی (از جمله کار دانشجویی)، خدمات، **مشاوره** | دانشگاه خودش |

## اداره مشاوره و سلامت روان (آنچه در نسخه قبل جا افتاده بود)
- متصدی دانشجو را با **شرح ماوقع** و نوع نگرانی (تغییر رفتار / خودآسیب‌رسانی / سایر) ارجاع می‌دهد ← سرپرست تأیید یا رد می‌کند ← اداره مشاوره دریافت، زمان‌بندی و ختم می‌کند.
- **ارجاع فوری (URGENT)** بدون انتظار برای تأیید سرپرست برای مشاوره قابل مشاهده است و سرپرست نمی‌تواند آن را رد کند.
- مشاوره فقط ارجاع‌ها را می‌بیند، نه فهرست کل دانشجویان؛ یادداشت بالینی مشاوره برای سرپرست و متصدی نمایش داده نمی‌شود.
- برنامه حضور روانشناسان در هر خوابگاه: `POST /counseling/schedules`؛ سرپرست و متصدی همان خوابگاه آن را می‌بینند.

## پیام‌رسانی و پیامک
- سه مدل گیرنده: مدیر سیستم ← کارکنان (خوابگاه/چند خوابگاه/همه، بر اساس نقش و پست کار دانشجویی)؛ سرپرست ← ساکنان خوابگاه خودش (فیلتر ساختمان/اتاق/وضعیت) یا کارکنان همان خوابگاه.
- `preview`: تعداد گیرندگان، بدون شماره معتبر، انصراف‌داده، تعداد پارت‌ها، هزینه تقریبی، موجودی و نمونه متن. ارسال بدون `force` در صورت کمبود موجودی رد می‌شود.
- متغیرها: `{{firstName}} {{lastName}} {{fullName}} {{dormitoryName}} {{date}}` (تاریخ شمسی).
- ارسال زمان‌بندی‌شده، قالب‌ها، لغو، سابقه با وضعیت هر گیرنده، گزارش تحویل (polling دوره‌ای)، تلاش مجدد ۳ بار با تأخیر افزایشی.
- لایه `ISmsProvider`: فعلاً `log` (توسعه) و `kavenegar`. با نوشتن یک کلاس دیگر، ارائه‌دهنده عوض می‌شود.
- سقف روزانه به تفکیک نقش: `SMS_DAILY_LIMITS` در `.env`.

## تصمیم‌های طراحی
- **جداسازی دانشگاه‌ها:** `universityId` هیچ‌وقت از ورودی کاربر خوانده نمی‌شود؛ خارج از دامنه ۴۰۴ برمی‌گردد.
- **بدون هم‌پوشانی در دیتابیس:** هر دانشجو حداکثر یک تخصیص فعال و هر تخت حداکثر یک ساکن فعال دارد (کلید یکتای nullable)، حتی با درخواست‌های هم‌زمان.
- **گردش‌کارها** (مرخصی، تعمیرات، ارجاع، چک‌لیست، گزارش) با شرط وضعیت در `UPDATE` محافظت شده‌اند تا دو تأیید هم‌زمان ممکن نباشد.
- گزارش‌های مهم متصدی فقط پس از «ارجاع سرپرست» به مدیر سیستم می‌رسد (طبق سند).
- پیوست‌ها: فقط PDF/PNG/JPEG با بررسی محتوای واقعی، حداکثر ۱۰ مگابایت، نام ذخیره‌سازی تصادفی، ذخیره روی دیسک پشت یک لایه که با S3/MinIO قابل تعویض است.
- تاریخ‌ها در دیتابیس میلادی‌اند؛ تبدیل ماه شمسی به بازه (`from/to`) با کلاینت است.

## فرض‌هایی که اگر غلط‌اند بگویید
1. کار دانشجویی = کاربر با نقش «متصدی» + `isStudentWorker` + پست (تصدی‌گری، پخش غذا، رابط حضور و غیاب، رابط بهداشت). همه‌ی پست‌ها دسترسی متصدی را دارند.
2. «دریافت غذا» و «تحویل اقلام غذایی» به‌صورت گزارش (وعده + تعداد) ثبت می‌شود، نه ثبت به‌ازای هر دانشجو.
3. مدیر سیستم و مدیر ارشد فقط گزارش‌های ارجاع‌شده‌ی سرپرست را می‌بینند.
4. دانشجو حساب ورود ندارد؛ پیام درون‌برنامه‌ای دانشجویان روی «تابلوی اعلان» تبلت خوابگاه نمایش داده می‌شود.
5. قانون اضافه‌کاری مشخص نیست؛ گزارش کارکرد ماهانه، دقایق کارکرد، شیفت برنامه‌ریزی‌شده، شیفت فوق‌العاده و مرخصی را جدا می‌دهد.

## تغییرات نسخه‌ی دوم

- **خوابگاه:** نوع (ملکی / استیجاری / خودگردان مشارکتی / خودگردان)، آدرس، موقعیت جغرافیایی (دکمه‌ی «گرفتن موقعیت از همین دستگاه»)؛ متراژ و سال ساخت حذف شد.
- **کاربران:** نوع استخدام (رسمی / قراردادی / قراردادی تبصره ۴ / شرکتی / ساعتی / طرحی) برای سرپرست، متصدی (غیر کار دانشجویی) و خدمات اجباری است. نقش‌های بالادستی می‌توانند مشخصات و نقش کاربران زیرمجموعه را ویرایش کنند (`PATCH /users/:id`) و رمز را ریست کنند (`POST /users/:id/reset-password`، قفل حساب را هم برمی‌دارد).
- **دانشجو:** موبایل اجباری؛ مقطع، تلفن ثابت، موبایل اولیاء (پدر/مادر)، شماره تماس ضروری (دوست/برادر/خواهر/نزدیکان). جنسیت برای سرپرست از نوع خوابگاه خودکار تعیین می‌شود.
- **داشبورد مدیر سیستم:** «حضور و غیاب امروز» و «گزارش ارجاعی هفته» از کارت‌ها حذف و به منو منتقل شدند.
- **آفلاین:** صفحه با Service Worker بدون اینترنت باز می‌شود؛ فهرست حضور و غیاب، دانشجویان و حضور من روی دستگاه ذخیره می‌ماند؛ ثبت حضور و غیاب، اعلام حضور/خروج و ارجاع به مشاوره در صف می‌رود و با برگشت اینترنت خودکار ارسال می‌شود. هر درخواست کلید `Idempotency-Key` دارد تا ارسال مجدد باعث ثبت تکراری نشود. زمان واقعی حضور/خروج با `clientTime` ثبت می‌شود.
  - برای Service Worker روی تبلت، آدرس باید **HTTPS** باشد (روی `localhost` بدون HTTPS هم کار می‌کند).
  - مدت اعتبار توکن (`JWT_EXPIRES_IN`) باید از طولانی‌ترین قطعی اینترنت بیشتر باشد؛ وگرنه برای ارسال تغییرات باید دوباره وارد شد (تغییرات از بین نمی‌روند).


## رابط بهداشت (نقش جدید)
- مدیر سیستم کاربر با نقش «رابط بهداشت» می‌سازد (می‌تواند قرارداد کار دانشجویی هم داشته باشد). این نقش به یک خوابگاه وصل نیست و در همه‌ی خوابگاه‌های دانشگاه بررسی می‌کند.
- **عناوین چک‌لیست** را خود رابط بهداشت در صفحه‌ی خودش تعریف می‌کند (افزودن، ویرایش، ترتیب، غیرفعال، حذف). یک فهرست برای همه‌ی خوابگاه‌هاست و سوابق قبلی با عوض‌شدن عناوین تغییر نمی‌کنند.
- **بررسی:** انتخاب خوابگاه، «سالم / مورد دارد» برای هر عنوان (شرح برای موارد دارای مشکل اجباری)، زمان بررسی خودکار ثبت می‌شود. بدون اینترنت هم کار می‌کند.
- **نمایش:** سرپرست (خوابگاه خودش)، مدیر سیستم و مدیر ارشد (دانشگاه خودشان)، مدیرکل (همه‌ی دانشگاه‌ها).
- **آلارم:** موارد دارای مشکل در داشبورد (بنر قرمز) و منوی «هشدارهای بهداشت» تا زمان رفع می‌مانند.
- **پاسخ سرپرست:** برای هر مورد «اقدامات انجام‌شده» و «موانع موجود» را می‌نویسد و در صورت رفع، مورد را «رفع‌شده» می‌کند. وضعیت‌ها: بدون اقدام ← در حال اقدام ← رفع‌شده.
- مسیرها: `/health-checks/items` · `/health-checks/inspections` · `/health-checks/alerts` · `PATCH /health-checks/results/:id/follow-up`. ماژول `health` را مدیرکل می‌تواند برای هر دانشگاه خاموش کند.


## قانون شیفت متصدیان
- شیفت از ساعت ۱۴ شروع و ساعت ۰۸ صبح روز بعد به سرپرست تحویل می‌شود (۱۸ ساعت). اگر صبح روز بعد تعطیل باشد، متصدی تا ساعت ۱۴ می‌ماند و به متصدی بعدی تحویل می‌دهد؛ این ۶ ساعت اضافه‌کاری است.
- ساعت‌ها و روزهای تعطیل هفتگی (پیش‌فرض: جمعه) و تعطیلات رسمی را مدیر سیستم تنظیم می‌کند (`GET/PUT /shifts/settings`، `/shifts/holidays` با ورودی تاریخ شمسی در رابط کاربری).
- **برنامه‌ی چرخشی** (`POST /shifts/generate`): متصدیان به ترتیب، هر روز یک نفر؛ با سه متصدی هر نفر هر سه روز یک شیفت دارد. `dryRun` پیش‌نمایش می‌دهد. تداخل با شیفت دیگر یا مرخصی تأییدشده رد و گزارش می‌شود.
- گزارش کارکرد ماهانه «اضافه‌کاری برنامه‌ای» (از برنامه) و «اضافه‌کاری انجام‌شده» (از ساعت خروج واقعی) را جدا می‌دهد.
- متصدی هنگام خروج می‌تواند گزارش تحویل شیفت بنویسد (`handoverNote`).
